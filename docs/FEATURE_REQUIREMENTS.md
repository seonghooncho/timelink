# Timelink 기능 요구사항 명세서

## 근본 목적

운영 중인 Timelink의 실제 사용자 기능, 제약 조건, 예외 처리 기준을 한 문서에 고정해 제품 변경과 구현 검증이 같은 기준을 바라보게 하는 것이 목적입니다.

## 비목적

이 문서는 API 필드 전체, 내부 인프라 구성, 상세 UI 디자인 토큰을 중복 설명하지 않습니다. API 계약은 `API_SPEC.md`, 배포 절차는 `infrastructure/DEPLOYMENT_NOTES.md`, 디자인 원칙은 `DESIGN_GUIDE.md`를 기준으로 합니다.

## 문서 기준

- 기준일: 2026-06-12
- 기준 커밋: `6c5cda0`
- 기준 서비스: 운영 도메인 `https://timelink.cloud`
- 대상 플랫폼: 모바일 우선 웹앱, 데스크톱 웹, PWA 설치 환경

## 사용자와 접근

### FR-AUTH-1. 로그인

- 사용자는 Google 또는 Kakao 소셜 로그인을 통해 서비스에 접근할 수 있어야 한다.
- 소셜 로그인 provider 설정이 없으면 로그인 화면에서 해당 provider를 사용할 수 없는 상태로 보여야 한다.
- 로그인 성공 후 사용자가 진입하려던 경로가 있으면 해당 경로로 복귀해야 한다.
- OAuth provider redirect URI와 프론트 콜백 페이지는 구분되어야 한다.

### FR-AUTH-2. 필수 약관 동의

- 최초 로그인 후 필수 약관과 개인정보처리방침 동의가 완료되지 않은 사용자는 서비스 주요 화면 진입 전에 동의 화면으로 유도되어야 한다.
- 소셜 로그인 버튼 클릭 전에 약관 체크를 강제하지 않고, 로그인 후 계정 상태 기준으로 한 번만 동의를 받는다.
- 필수 동의가 완료된 사용자는 동의 화면을 다시 거치지 않아야 한다.

### FR-PROFILE-1. 프로필 생성과 갱신

- 신규 소셜 로그인 사용자는 provider에서 동의된 닉네임과 프로필 사진을 가져와 초기 프로필에 반영해야 한다.
- Kakao에서 닉네임 또는 프로필 사진 동의가 없거나 값이 비어 있으면 생성형 기본 닉네임과 기본 이미지로 대체해야 한다.
- 사용자가 이미 직접 설정한 닉네임이나 프로필 사진이 있으면 소셜 로그인 hint로 덮어쓰지 않아야 한다.
- 사용자가 프로필 사진과 닉네임을 변경하면 그룹 멤버 목록에서도 최신 프로필 정보가 우선 표시되어야 한다.

## 홈

### FR-HOME-1. 오늘 기준 일정 표시

- 홈 화면의 타임테이블과 일정 카드는 기본적으로 오늘 날짜 기준의 일정을 보여야 한다.
- 오늘 이전 일정이 있으면 일정 카드 왼쪽에 일부가 살짝 보이게 해 지난 일정도 볼 수 있음을 인지시켜야 한다.
- 사용자는 좌우 스크롤로 과거와 미래 일정을 탐색할 수 있어야 한다.

### FR-HOME-2. 타임테이블

- 홈 타임테이블의 일정 블록은 `시작 일시 + 소요시간`으로 계산한 시간 구간에 표시되어야 한다.
- 같은 시간대에 여러 일정이 겹치거나 시작 시간이 다르면 서로 구분되게 배치되어야 한다.
- 타임슬롯에는 시작시간만 간략히 표시하고, 날짜와 소요시간은 중복 표기하지 않는다.
- 스크롤로 내려가는 영역에도 시간 구분선이 끊기지 않아야 한다.

### FR-HOME-3. 일정 카드 상태

- 일정 완료 버튼은 삭제와 독립적으로 동작해야 한다.
- 완료 처리된 일정은 카드의 완료 표시가 채워진 상태로 보여야 하며, 다시 누르면 완료 해제되어야 한다.
- 삭제 확인 모달에서 유지 또는 취소를 눌러도 완료 상태 변경은 유지되어야 한다.

## 일정

### FR-SCHEDULE-1. 일정 데이터 모델

- 일정 생성과 수정은 종료시간을 직접 입력받지 않고 날짜, 시작 시간, 소요시간으로 표현한다.
- 소요시간을 사용자가 따로 바꾸지 않으면 기본값은 1시간이어야 한다.
- 백엔드는 호환 목적의 종료시간 필드를 유지할 수 있지만, 신규 계산 기준은 `startTime + duration`이어야 한다.
- `startTime + duration`이 같은 날짜를 넘어가는 일정은 생성 또는 수정할 수 없어야 한다.

### FR-SCHEDULE-2. 일정 생성

- 사용자는 카테고리, 제목, 내용, 날짜, 시작 시간, 소요시간, 중요 여부, 알림 여부를 입력해 일정을 만들 수 있어야 한다.
- 시작 시간은 프론트 UI에서 30분 단위로만 선택 가능해야 한다.
- 조건이 맞지 않는 상태에서 등록 버튼을 누르면 어떤 조건이 문제인지 토스트로 알려야 한다.
- 그룹 상세에서 그룹 일정 생성으로 진입한 경우 선택된 그룹 정보가 일정에 연결되어야 한다.
- 사진 업로드 기반 AI 일정 분석은 포스터, 메시지, 캘린더 이미지 등에서 일정 후보를 추출해 폼에 채울 수 있어야 한다.

### FR-SCHEDULE-3. 일정 상세와 수정

- 일정 클릭 시 기본 상태는 읽기 전용 상세 모달이어야 한다.
- 사용자가 수정 버튼을 누른 경우에만 수정 가능한 모달 상태로 전환되어야 한다.
- 모달을 닫고 다시 열면 항상 읽기 전용 상세 상태로 시작해야 한다.
- 일정 수정에서는 제목, 내용, 카테고리, 중요 여부, 알림 여부, 일시, 소요시간을 수정할 수 있어야 한다.
- 일정 상세 모달에는 작은 삭제 버튼이 제공되어야 한다.

### FR-SCHEDULE-4. 캘린더

- 캘린더 날짜를 선택하면 해당 날짜의 일정 목록을 일정 섹션에서 확인할 수 있어야 한다.
- 일정 섹션에 항목이 많으면 섹션 내부에서 스크롤하고, 보이지 않는 방향에 항목이 있으면 그라데이션으로 스크롤 가능성을 알려야 한다.
- 일정 섹션 내부 스크롤바는 사용자가 스크롤 가능한 영역임을 인지할 수 있게 보여야 한다.

## 그룹

### FR-GROUP-1. 나의 그룹

- 사용자는 자신이 참여한 그룹 목록을 확인할 수 있어야 한다.
- 참여 그룹이 없으면 그룹 생성과 초대 링크 참여 흐름을 안내하는 빈 상태가 표시되어야 한다.
- 그룹 목록은 커서 페이지네이션을 사용하며 기본 20개 단위로 조회해야 한다.
- 다음 페이지가 있으면 `그룹 더보기`로 이어서 불러올 수 있어야 한다.

### FR-GROUP-2. 그룹 생성과 참여

- 사용자는 그룹 이름, 설명, 이미지를 입력해 그룹을 만들 수 있어야 한다.
- 그룹 생성자는 자동으로 관리자 멤버가 되어야 한다.
- 사용자는 초대 링크를 통해 그룹 참여 화면으로 진입하고 그룹에 가입할 수 있어야 한다.
- 이미 가입한 사용자가 같은 초대 링크로 들어오면 중복 가입 대신 그룹 상세로 이동해야 한다.

### FR-GROUP-3. 그룹 상세

- 그룹 상세에서는 그룹 정보, 참여 멤버, 확정된 그룹 일정, 조율 중인 일정을 확인할 수 있어야 한다.
- 그룹 일정과 조율 중인 일정 섹션은 항목이 많으면 내부 스크롤과 그라데이션으로 처리해야 한다.
- 그룹 상세 하단에는 그룹 일정 생성과 시간 조율하기 버튼이 항상 접근 가능한 고정 영역으로 제공되어야 한다.
- 그룹 상세에서 직접 URL로 진입해도 뒤로가기 버튼은 논리적으로 나의 그룹 또는 상위 그룹 화면으로 이동해야 한다.

### FR-GROUP-4. 그룹 정보 수정과 멤버 관리

- 그룹 헤더 메뉴는 햄버거 버튼 아래의 현재 위치 기준으로 열려야 하며, 바깥 영역을 클릭하면 닫혀야 한다.
- 모든 그룹 멤버는 그룹 이름과 설명을 수정할 수 있어야 한다.
- 관리자는 멤버 관리 화면에서 자신을 제외한 다른 멤버를 내보낼 수 있어야 한다.
- 참여 멤버 영역은 기본적으로 클릭 가능해야 하며, 클릭 시 프로필 목록 모달을 열어야 한다.
- 참여 멤버 모달은 항목이 많아도 일정 높이 이상 무한히 커지지 않고 내부 스크롤로 처리해야 한다.

## 시간 조율

### FR-COORD-1. 조율 대상과 생성

- 시간 조율 대상은 그룹 전체 멤버로 정의한다.
- 조율 생성자는 자동으로 조율 대상에 포함되어야 한다.
- 조율 생성 시 후보 날짜, 시작 시간대, 종료 시간대, 조율 제목을 설정할 수 있어야 한다.
- 후보 날짜가 5일 이하이면 한 화면에서 모두 보여야 한다.
- 후보 날짜가 5일을 초과하면 5개 단위로 날짜 묶음을 이동하며, 첫 페이지와 마지막 페이지는 항상 5개 날짜가 보이도록 중복 표시를 허용한다.

### FR-COORD-2. 내 가능한 시간

- 사용자는 후보 날짜와 시간대에서 자신이 가능한 슬롯을 선택할 수 있어야 한다.
- 기존 내 일정은 시간 조율 타임테이블 위에 반투명하게 깔려 보여야 한다.
- 사용자가 선택한 가능 시간은 기존 일정 위에 투명도 있는 색상으로 표시되어, 기존 일정과 선택 상태를 동시에 파악할 수 있어야 한다.
- 응답 저장, 수정, 삭제 실패는 토스트로 알려야 한다.

### FR-COORD-3. 모두 가능한 시간

- 모두 가능한 시간 화면은 슬롯별 투표 수와 참여자를 확인할 수 있어야 한다.
- 타임슬롯을 선택하면 해당 슬롯을 선택한 사용자의 프로필 사진과 이름을 모달로 보여야 한다.
- 식별자 문자열만 노출하지 않아야 한다.
- 모두 가능한 시간 섹션 진입 초기에는 가장 많이 투표되었고 연속으로 오래 겹치는 추천 슬롯을 잠시 모달로 보여야 한다.
- 추천 모달에는 `타임슬롯을 선택하면 투표 인원을 확인할 수 있어요.`와 같은 짧은 안내가 포함되어야 한다.
- 모든 멤버가 가능한 시간이 있으면 그룹 일정 생성하기 버튼으로 확정 일정을 만들 수 있어야 한다.

## 알림

### FR-NOTI-1. 알림센터

- 사용자는 알림센터에서 일정 알림과 그룹 알림을 탭으로 구분해 확인할 수 있어야 한다.
- 알림 목록은 커서 페이지네이션을 사용하며 기본 20개 단위로 조회해야 한다.
- 읽지 않은 알림은 시각적으로 구분되어야 하며, 사용자가 알림을 누르면 읽음 처리되어야 한다.
- 그룹 활동 알림은 사용자가 별도로 끄지 않아도 알림센터에 기본 저장되어야 한다.

### FR-NOTI-2. 알림 설정

- 푸시 알림 설정의 기본값은 꺼짐이어야 한다.
- 일정 알림이 꺼져 있으면 일정 알림센터 기록, 실시간 인앱 알림, 예약 리마인드가 생성되지 않아야 한다.
- 일정 알림이 꺼져 있으면 1일 전 리마인드, 당일 리마인드, 중요 일정 알림은 켤 수 없는 비활성 상태여야 한다.
- 일정 알림이 켜져 있을 때만 리마인드 알림들을 사용자가 켤 수 있어야 한다.
- 그룹 알림은 별도 on/off 없이 그룹 일정 생성, 시간 조율 생성, 멤버 참여 등 그룹 활동을 대상으로 한다.
- 푸시 알림은 일정/그룹 알림과 분리된 별도 설정이며, 브라우저/OS 권한과 사용자 설정이 켜진 경우에만 발송되어야 한다.
- 브라우저 알림 권한이 꺼져 있거나 푸시 준비가 되지 않아도 알림센터에서 확인 가능한 상태를 유지해야 한다.

### FR-NOTI-3. 푸시와 리마인드

- 푸시는 Web Push VAPID 기반으로 동작하며, 브라우저 service worker와 push subscription을 사용한다.
- 최초 필수 동의 완료 직후와 푸시 알림을 켜는 시점에 브라우저 알림 권한을 유도할 수 있어야 한다.
- 일정 리마인드는 운영 초기 기준으로 알림마다 EventBridge Scheduler를 생성하고 Lambda worker가 발송하는 구조를 사용한다.
- 일정이 생성, 수정, 삭제되면 관련 리마인드 예약도 재계산되거나 제거되어야 한다.

## PWA

### FR-PWA-1. 설치 유도

- 모바일에서는 브라우저별 공유 메뉴와 홈 화면에 추가하기 흐름을 짧게 안내해야 한다.
- 데스크톱에서는 설치 이벤트를 사용할 수 있으면 직접 설치 버튼을 제공해야 한다.
- 설치 유도 메시지는 상단에 작게 노출되어 주요 작업을 방해하지 않아야 한다.
- 이미 설치된 상태이거나 사용자가 닫은 상태에서는 반복적으로 과하게 노출하지 않아야 한다.

## 마이페이지

### FR-MY-1. 프로필

- 사용자는 마이페이지에서 프로필 사진과 닉네임을 수정할 수 있어야 한다.
- 프로필 이미지는 jpg, png, webp만 허용하고, 15MB를 초과하면 업로드 전에 거부해야 한다.
- 프로필/그룹 사진은 선택 후 바로 업로드하지 않고 crop/position 조정 UI를 거쳐야 한다.
- 이미지 변환이 끝나기 전에는 처리 중 상태를 표시하고, 실패 시 기본 이미지와 실패 메시지를 보여줘야 한다.
- 프로필 수정 성공과 실패는 토스트로 알려야 한다.

### FR-MY-2. 사용 팁 영역

- 마이페이지의 프로필 섹션과 알림 설정 섹션 사이에는 짧은 사용 팁 영역을 제공한다.
- 팁은 서비스 사용 중 알면 좋은 기능 안내 10개 이상을 제공하고, 사용자는 좌우 화살표로 다른 팁을 볼 수 있어야 한다.
- 팁은 5초마다 자동으로 다음 항목으로 넘어가야 한다.
- 팁 영역은 추후 광고 또는 운영 공지 영역으로 확장할 수 있도록 독립 섹션으로 유지한다.
- 팁은 한두 줄 수준으로 유지해 알림 설정 영역을 과도하게 밀어내지 않아야 한다.

## 공통 UX와 예외 처리

### FR-COMMON-1. 토스트

- 사용자가 버튼을 눌러 수행하는 생성, 수정, 삭제, 저장, 업로드, 읽음 처리, 로그아웃 같은 작업은 실패 시 일관된 토스트로 문제를 알려야 한다.
- 사용자가 고칠 수 있는 입력 오류는 가능한 한 어떤 조건이 문제인지 구체적으로 알려야 한다.
- 성공 토스트는 작업 완료를 짧게 확인하는 수준으로 유지한다.

### FR-COMMON-2. 목록과 스크롤

- 일정, 그룹, 알림, 조율처럼 항목 수가 늘어날 수 있는 목록은 페이지네이션, 내부 스크롤, 더보기 중 하나로 상한을 관리해야 한다.
- 화면 하단 푸터 또는 고정 버튼 영역에 의해 마지막 항목이 가려지지 않아야 한다.
- 내부 스크롤 영역은 스크롤바와 동적 그라데이션으로 추가 항목 존재 여부를 알려야 한다.
- 모달 또는 바텀시트는 항목 수가 많아도 무한정 높아지지 않고 내부 스크롤로 처리해야 한다.

### FR-COMMON-3. 텍스트와 긴 데이터

- 제목, 그룹명, 닉네임처럼 길어질 수 있는 텍스트는 부모 영역을 깨지 않도록 줄임 또는 줄바꿈 정책을 가져야 한다.
- 사용자가 생성하는 이름과 설명은 화면 폭이 좁아도 버튼, 아이콘, 다음 항목과 겹치지 않아야 한다.

### FR-COMMON-4. 페이지네이션 기본값

- 일정, 알림, 조율, 그룹 목록 API는 커서 기반 페이지네이션을 기본으로 한다.
- 목록 API의 기본 조회 개수는 20개이며, 과도한 요청은 백엔드에서 최대값으로 제한해야 한다.
- 홈과 캘린더처럼 화면 목적상 더 넓은 기간의 일정이 필요한 경우 프론트가 명시적으로 더 큰 limit을 요청할 수 있다.

## 법적 고지와 개인정보

### FR-LEGAL-1. 약관과 개인정보처리방침

- 서비스는 이용약관과 개인정보처리방침 페이지를 제공해야 한다.
- 개인정보처리방침은 소셜 로그인 정보, 일정/그룹/조율 데이터, 알림 설정, 푸시 구독 정보, 업로드 이미지 URL 같은 처리 항목을 설명해야 한다.
- 필수 동의 상태는 사용자 프로필에 저장되어야 한다.

### FR-LEGAL-2. 개인정보 최소 노출

- 시간 조율 투표자, 그룹 멤버 등 사용자 표시가 필요한 곳에서는 내부 식별자 대신 프로필 사진과 닉네임을 우선 사용해야 한다.
- 내부 userId는 일반 사용자 UI에 직접 노출하지 않는 것을 원칙으로 한다.

- 광고 집행, 노출 빈도 제한, 클릭 추적은 아직 구현 요구사항이 아니다.
